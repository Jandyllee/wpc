# Hostinger Admin Account Setup

This guide covers how to provision and protect the WESTPRIME CONFESSIONS admin
account when deploying the site to Hostinger. It is intentionally separate from
the general project setup notes.

## Important: how the current admin login works

The current admin login looks up a database row whose username is exactly
`admin` and whose role is `admin`. Keep that username for the first production
deployment unless the application code is changed and tested to support a
different admin username.

The database schema does not create an admin account. Provision one explicitly
with a password hash generated locally, as described below.

## Recommended deployment approach

Provision the admin deliberately as part of deployment:

1. Prepare a unique, strong admin password using a password manager. Do not
   reuse an email, database, or personal account password. A password of at
   least 16 randomly generated characters is recommended.
2. Create and select the production database and database user in Hostinger.
   Import the reviewed production schema using Hostinger's phpMyAdmin.
3. Generate a password hash locally with PHP. Do not use a public online
   password-hash generator and do not put the plaintext password in this
   document, source code, SQL, a screenshot, or a public repository.
4. Create the admin row using the generated hash (instructions below).
5. Verify the account and test the admin login before opening the site to
   visitors.
6. Store the password in a password manager and keep the production database
   credentials and SMTP credentials in Hostinger's private configuration,
   not in the public website files.

The application now requires production database environment variables:
`WPC_DB_HOST`, `WPC_DB_NAME`, `WPC_DB_USER`, and `WPC_DB_PASSWORD`. Configure
these through Hostinger's private PHP environment/configuration facility before
opening the site. The local XAMPP-only fallback is not used for a named
production host.

If the schema has already been imported, check whether an `admin` account
already exists before creating one. If it exists, use the **Replace the
password on an existing account** instructions below to set a new hash before
the site is publicly accessible.

## Generate a password hash locally

Use PHP from your local XAMPP installation, not a remote hash service. For
example, create a temporary PHP CLI script outside the project directory:

```php
<?php
$password = readline('Enter the new admin password: ');
if ($password === false || strlen($password) < 16) {
    fwrite(STDERR, "Password must be at least 16 characters.\n");
    exit(1);
}
echo password_hash($password, PASSWORD_DEFAULT), PHP_EOL;
```

Run it with XAMPP's PHP CLI, for example:

```powershell
C:\xampp\php\php.exe C:\path\outside\the\project\make-admin-hash.php
```

Enter a unique password generated by your password manager. Copy only the
resulting hash for the database operation. Delete the temporary script after
use, and do not upload it to Hostinger. The password is entered at the local
console; take care that nobody can see the terminal while you enter it.

If the local PHP CLI does not provide `readline()`, use an equivalent local,
private PHP method to generate the hash. Do not switch to an online generator.

## Create a new admin row

Use this when the production database has no admin account. In Hostinger
phpMyAdmin, select the production database and run the following query after
replacing the email and hash placeholders with your own values:

```sql
INSERT INTO users (username, email, password_hash, role)
VALUES ('admin', 'your-admin-email@example.com', 'PASTE_LOCAL_HASH_HERE', 'admin');
```

The hash placeholder must be the output of local PHP's `password_hash()`.
Never put the plaintext password in the SQL statement.

If the query reports that `admin` already exists, do not create another account
with a different name. Follow the next section to replace the existing admin
password hash.

## Replace the password on an existing account

If an `admin` account already exists, run this query before public launch,
replacing the hash placeholder with the locally generated hash:

```sql
UPDATE users
SET email = 'your-admin-email@example.com',
    password_hash = 'PASTE_LOCAL_HASH_HERE',
    role = 'admin'
WHERE username = 'admin';
```

Then check that exactly one account has the expected username and admin role.
Do not select or publish its password hash:

```sql
SELECT id, username, email, role
FROM users
WHERE username = 'admin';
```

Confirm the result contains exactly one row, the intended recovery email, and
the `admin` role. If it returns no rows or multiple unexpected results, stop
and inspect the production database before continuing.

## Test before launch

1. Use the admin page over the production HTTPS URL.
2. Sign in as `admin` using the new password.
3. Verify that the dashboard opens and that admin-only moderation actions work.
4. Sign out and confirm the admin session is cleared.
5. Use the password recovery flow only after confirming that the account's
   email address is correct and the production SMTP configuration works.
6. Check that an incorrect password is rejected.
7. Do not leave a database-management or password-generation script in the
   public web directory.

If any test fails, keep the site private or in maintenance mode until the
problem is resolved.

## Password and account maintenance

- Keep the admin password in a trusted password manager. Do not share it through
  chat, email, source control, or this guide.
- Use a unique password and change it immediately if it is shared, exposed, or
  suspected to be compromised.
- Keep the admin recovery email current and protected by its own unique
  password and multi-factor authentication where available.
- Restrict access to Hostinger, phpMyAdmin, and the mailbox to trusted
  administrators. Use HTTPS and enable multi-factor authentication on the
  hosting account when offered.
- Take a database backup before changing account records. Store backups
  privately; they contain password hashes and user data.
- Do not use the local XAMPP database account or local development password as
  the Hostinger production database account.
- Do not put database or SMTP secrets in this file or any other tracked file.
  Configure production credentials through Hostinger's supported private
  environment/configuration mechanism.

## If a credential was exposed

Changing or deleting a credential in the current files does not invalidate the
credential itself and may not remove it from repository history. Immediately
change the affected password in the provider or production database, update the
private Hostinger configuration if necessary, and review account activity and
repository access. Do not rely on deleting a file or editing Git history as a
replacement for rotating the credential.

## Current limitation

The admin login currently requires the username `admin`; it is not a general
login for any account whose role is `admin`. If you want to promote a different
username to admin, first update and test the application's admin-login lookup.
Do not assume that setting another user's role to `admin` alone will let that
user sign in through the current admin login screen.
